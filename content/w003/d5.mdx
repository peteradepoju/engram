<Step n={1} title="Hidden state" minutes={25} />

Notebooks are wonderful for exploring: you run a cell, look, change it, run it again. But a notebook remembers everything you ran, in the order you ran it, including cells you have since deleted or edited. The variables in memory can stop matching the code on the page. This is **hidden state**, and it is the most common reason a notebook gives a different answer the next day.

The lesson pages here work the same way: cells on a page share one Python, like a notebook. Try it.

<PyCell code={String.raw`
  threshold = 0.5
`} />

<PyCell code={String.raw`
  import numpy as np
  rts = np.array([0.31, 0.62, 0.45, 0.88, 0.52])
  print("slow trials:", (rts > threshold).sum())
`} />

Now change the first cell to `threshold = 0.6` but **do not run it**, and run the second cell again. The answer is still computed with 0.5, although the page now says 0.6. In a long notebook that kind of mismatch is invisible.

Three habits prevent it:

1. Before trusting a notebook, **restart and run all** cells from the top (in Colab: Runtime, then Restart and run all).
2. Write **functions that take their inputs as arguments** instead of reading global variables.
3. Once code is stable, move it out of the notebook into a **module** (a `.py` file) and import it.

<Step n={2} title="Code in modules" minutes={25} />

A **module** is just a Python file. Code in a module is written once, tested once and imported everywhere, so every notebook and script uses the same version. The in-page Python has its own small file system, so you can write a module and import it right here.

<PyCell code={String.raw`
  import os, sys, importlib
  code = '''
  """Small tools for analysing decision-making sessions."""
  import numpy as np

  def proportion_right(choices):
      """Fraction of responses that were 'right' (choice == 1), ignoring no-response trials (0)."""
      choices = np.asarray(choices)
      valid = choices[choices != 0]
      return float((valid == 1).mean())
  '''
  os.makedirs("src", exist_ok=True)
  open("src/behaviour.py", "w").write(code)
  sys.path.insert(0, os.path.abspath("src"))
  importlib.invalidate_caches()
  import behaviour
  print(behaviour.proportion_right([1, -1, 1, 0, 1]))
  help(behaviour.proportion_right)
`} />

In a real project, the notebook becomes a thin layer: it imports from `src/`, calls functions and shows figures. When you change the module, every analysis that uses it changes in the same way, and the tests you wrote in Week 1 catch mistakes.

<Step n={3} title="Environments, seeds and provenance" minutes={30} />

Code also depends on the exact versions of NumPy, pandas, SciPy and Python. A function can change its default between versions and quietly change your result. So record the **environment**:

<PyCell code={String.raw`
  import sys, platform, numpy, pandas, scipy, matplotlib
  print("Python", sys.version.split()[0], "on", platform.system())
  for m in [numpy, pandas, scipy, matplotlib]:
      print(f"{m.__name__}=={m.__version__}")
`} />

Those lines, saved in a `requirements.txt` file, let anyone rebuild your environment (`pip install -r requirements.txt`, or `uv pip install -r requirements.txt`). Conda users keep an `environment.yml` instead.

A result also depends on its **inputs** and its **random seed**. Saving all of this next to the result is called **provenance**: a record of exactly how it was made.

In a Git repository you would also store the **commit hash** of the code that made the result (`git rev-parse HEAD`). Then every number in a paper points to the exact code, data and environment that produced it.

<Prove title="Why automation matters" task="An analysis has $k$ independent manual steps, each with probability $q$ of a silent mistake. Find the probability that the whole analysis is mistake-free. Evaluate it for $k = 10$, $q = 0.02$ and for $k = 50$, $q = 0.02$.">

Each step is correct with probability $1 - q$, independently, so all $k$ are correct with probability $(1 - q)^k$.

For $k = 10$: $0.98^{10} \approx 0.82$. Nearly one analysis in five contains a mistake.

For $k = 50$: $0.98^{50} \approx 0.36$. Most such analyses are wrong somewhere.

A script has the same steps but performs them identically every time, and its mistakes can be found once and fixed for good. That is the argument for automating every step, rule 1 of today's paper.

</Prove>

<Step n={4} title="Git branches" minutes={25} />

You will often want to try something risky: a new smoothing method, a different trial selection, a refactor. A **branch** is a separate line of commits. You work on the branch, and `main` stays exactly as it was. If the idea works, you **merge** it into `main`; if not, you delete the branch.
